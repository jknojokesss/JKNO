## PR #9 — QuickBooks Online read pipe

`2026-08-12` · branch `claude/roofing-demo-2ka9v8` · closed

One Intuit app ("PL Pull") → live P&L feeds for any client, read-only:

- Accounting scope only, sandbox by default (`QBO_ENV=production` to flip). Endpoints respond with a clear "not configured" message until `QBO_CLIENT_ID`/`QBO_CLIENT_SECRET` exist in the environment, so deploying this is inert.

Also documents the pipe in CLAUDE.md and `.env.local.example`.

## PR #14 — QBO: Balance Sheet + General Ledger detail

`2026-08-12` · branch `claude/roofing-demo-2ka9v8` · closed

Extends the QBO pipe from P&L-only to the full books.

**Balance Sheet** — the monthly summary parser is now generic (P&L and BS share it) and additionally captures the nearest enclosing header as `subgroup`, so rows carry both the top-level section (ASSETS / LIABILITIES AND EQUITY) and the detail grouping (Bank Accounts, Current Liabilities, …). Lands in `qbo_bs_summary`.

**General Ledger** — transaction-level rows (date, type, doc num, name, memo, split account, account, amount) in `qbo_gl_txns`. Two deliberate choices: pulled **one month per request**, since a long-range GL report is the usual way to hit Intuit's report timeout and per-month windows make partial failures cheap to retry; and columns are located by **ColKey** rather than position, because the GL column set varies by company configuration.

**Sync behavior** — nightly: P&L + BS full replace over 24 months, GL for the trailing 3 months, replacing only those months so history accumulates rather than being re-pulled every night. `?gl=` widens the GL window for a backfill (max 36), `?client=` limits to one client. Each report is independent — one failing no longer costs the others, and the connection records which ones failed.

Migration applied for the two tables plus `subgroup` on `qbo_gl_summary`.

Note: the GL and BS parsers have not yet seen a live response — they're written from Intuit's documented report shapes and need verification against real data on the first run, the same way the P&L parser's Total-column bug only surfaced live.

## PR #16 — QBO GL: robust column matching + shape reporting on empty pulls

`2026-08-12` · branch `claude/roofing-demo-2ka9v8` · closed

First live General Ledger pull returned **0 rows across 24 months** while P&L (71) and Balance Sheet (169) landed correctly — so the book isn't empty, the parse was.

Cause: column lookup matched only on `MetaData.ColKey`. When that shape isn't present every index resolved to `-1`, so the date/amount guard skipped every data row.

Fixes:
- Columns are matched on `ColKey`, `ColType`, **or** `ColTitle`, with synonyms (`Date`/`tx_date`, `Num`/`doc_num`, `Memo/Description`, `Split`, `Amount`, …).
- The request now names the desired column set explicitly rather than relying on the per-company default.
- Data rows fall back to positional reads (date first, amount last) when a column still can't be located, with an ISO-date guard so subtotal and beginning-balance rows stay excluded.
- A zero-row pull now returns the response's actual column descriptors (`index:title|type=|key=`) in the sync result, so the next run diagnoses itself instead of reporting a bare `0`.

## PR #18 — Fix: QBO mirror truncated portal data at 1000 rows

`2026-08-12` · branch `claude/roofing-demo-2ka9v8` · closed

**Bug (hit in production):** PostgREST caps a `select` at 1000 rows unless paged. The mirror's reads were unbounded, so on Reydel (~6,900 transactions) the first live run backed up only 1,000 rows, deleted every row in range — `delete` is *not* capped — and reinserted only 1,000. His portal went from 6,790 rows to 1,000 (January only).

Data was fully recovered: `qbo_gl_txns` held the complete 6,887-row pull, so the portal was restored in SQL, which has no such cap.

**Fixes:**
- `selectAll()` pages reads to completion; all mirror reads use it.
- The replacement set is read **first** and its count compared against the pull — a short read now aborts before anything is deleted.
- The delete is error-checked (it previously ignored its error).
- After insert, the resulting row count is verified against what was written, and a mismatch raises with a pointer to `gl_mirror_backup`.

Chasing a $531 discrepancy in Jerky's balance sheet turned up a genuine bug in the pagination added in #18.

`selectAll()` pages with `.range()` but specified no `.order()`. Postgres makes no guarantee that row order is identical between separate requests, so page boundaries drift: some rows come back in two pages, others in none. **The total row count stays correct**, which is why the mirror's own count verification passed — but the contents are wrong.

The gap being *constant across every month* from January onward is what gave it away — a missing or extra transaction shows up once and then persists, whereas a systematic parsing problem would drift.

Fix: `selectAll()` now orders by primary key. Jerky's ledger was re-mirrored directly in SQL and re-verified — **all 11 balance-sheet accounts now reconcile to QuickBooks exactly, zero differing**.
